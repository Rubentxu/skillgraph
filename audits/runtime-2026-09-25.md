## 3. Findings rankeados

### F-1 — Inconsistencia: `_snapshot` usa `EventLog.events_for_run` en lugar de `Storage.list_events_for_run`  · **MAYOR**

**Severidad**: MAYOR (consistencia / claridad arquitectónica).
**Localización**: `src/skillgraph/runtime/runcontroller.py:1346-1352`.

**Observación**:

```python
def _snapshot(self, tenant_id, project_id, run_id):
    ...
    events_emitted = (
        len(
            self._events.events_for_run(  # ← EventLog
                tenant_id=tenant_id,
                project_id=project_id,
                run_id=run_id,
            )
        ),
    )
```

El resto del módulo (líneas 699 y 727) usa
`self._storage.list_events_for_run(...)` para la **misma operación
semántica**: contar/listar eventos de un run. La diferencia es que
`EventLog.events_for_run` retorna `list[dict]` (parsed) y
`Storage.list_events_for_run` retorna `list[sqlite3.Row]`.

Comparación:

| Línea | API | Lo que hace |
|---|---|---|
| 1347 | `self._events.events_for_run` | cuenta elementos parseados |
| 699 / 727 | `self._storage.list_events_for_run` | cuenta `Row` directas |

Ambas ejecutan la misma query SQL (verificada:
`Storage.list_events_for_run` líneas 1268-1287 y
`EventLog.events_for_run` líneas 205-216 son idénticas en WHERE/ORDER BY).

**Por qué importa**: el resto del módulo se ha movido a delegar en
`Storage.*` (regla "Storage encapsula SQL", explícita en el comentario
de la línea 696-697). El `_snapshot` es el único punto donde el
RunController todavía lee vía `EventLog`. Si el comentario de la línea
696 es la regla vigente, este sitio es la excepción.

**Defensa de NO actuar ahora**:

1. El resultado es idéntico (la query es la misma).
2. No causa bug observable.
3. Cambiarlo requiere verificación de que `EventLog.events_for_run` y
   `Storage.list_events_for_run` siguen siendo idénticas hoy (que sí
   lo son, pero un cambio futuro podría divergir silenciosamente).
4. Es 1 línea de código modificada; requiere test de no-regresión.

**Acción recomendada**: **Opcional**. Si se ejecuta, refactor de
consistencia + 1 test de regresión. ~5 LoC. Sin bump de release.
Etiquetar como `style(consistency)` o `refactor(snapshot-source)`.

### F-4 — Inconsistencia de `sort_keys` en serialización JSON  · **MENOR**

**Severidad**: MENOR (estilo / contrato).
**Localización**: `runcontroller.py:1015` vs `1242`.

```python
# línea 1015: handoff_json
handoff_json = json.dumps(handoff.to_dict(), sort_keys=False)

# línea 1242: result_json
result_json = json.dumps(result_to_jsonable(result), sort_keys=True)
```

Dos serializaciones JSON con políticas distintas:
- `sort_keys=False`: preserva el orden del `to_dict()` de Handoff
  (que ya ordena manualmente en sus campos internos).
- `sort_keys=True`: ordena lexicográficamente las claves del
  `result_to_jsonable()`.

**Análisis**:

- `handoff.to_dict()` ya ordena manualmente `budget` (`sorted(items())`)
  y `capabilities` (`sorted(...)`), pero el resto de campos siguen el
  orden de declaración. Por eso `sort_keys=False` es coherente con
  el contrato "orden total, sin orden de inserción" del Handoff.
- `result_to_jsonable` retorna un dict de 3 claves (`outcome`, `result`,
  `evidence_ref`) en orden de declaración; `sort_keys=True` las
  reordena. Esto produce un JSON distinto del dict original en
  disco.

No causa bug (ambos son deterministas), pero el segundo introduce una
redundancia: serializa un dict ordenado por declaración y luego lo
re-ordena por clave. O se quiere orden determinista global
(`sort_keys=True`) o se quiere preservar orden declarado (`sort_keys=False`).

**Acción recomendada**: Decidir una política y aplicarla a ambos. Más
limpio: `sort_keys=True` en ambos (contrato "JSON estable" bien definido).
~2 LoC. Sin bump.

### F-6 — OBSERVACIÓN: la grieta transaccional residual está documentada pero no resuelta  · **DELEGABLE**

**Severidad**: NO accionable en este ciclo (deuda defendible ya
documentada). **OBSERVACIÓN** arquitectónica.
**Localización**: `docs/architecture/h9-plan-b-atomicity-characterization.md`
§2 + `STATE.yaml` `deuda_tecnica_residual`.

**Observación**: Las 5 grietas transaccionales A, B, C, D, E, G
están CERRADAS por las operaciones atómicas de Storage
(`create_run_atomically`, `start_node_execution_atomically`,
`complete_node_execution_atomically`, `mark_node_failed_atomically`,
`transition_run_state_atomically`). La grieta F (`recover_interrupted`)
NO requiere atomicidad por contrato (no emite evento del Adapter).

**Lo que queda fuera del alcance del RunController**:

1. **Concurrencia multi-proceso sobre `transition_run_state_atomically`**
   (mencionado en el spec §2 "Fuera del slice 4"). Los locks S6
   v0.14.0 mitigan interleaving a nivel de filesystem, no resuelven
   la transaccionalidad cross-proceso. La prueba con `multiprocessing`
   en `test_locks.py` cubre serialización, no atomicidad.
2. **Recuperación tras `os._exit` / kill -9** (spec §7 riesgo 2): WAL
   checkpointea automáticamente, pero no se ha certificado empíricamente.
3. **Backup/restore externo**: consistencia entre snapshot SQLite y
   event log. Fuera de scope.

Estos 3 puntos están **explícitamente** fuera del scope del RunController
y son defendibles como deuda diferida a S7+ del blueprint. El
`audits/h9-limitacion-7-closure.md` confirma que la fragilidad
transaccional preexistente (limitacion-7) está cerrada.

**Acción recomendada**: **Ninguna** en este ciclo. Mantener la deuda
documentada. Si en el futuro el operador aprueba S7+, evaluar estos
3 puntos como candidatos.
